# Operator-list reads v1

This independently negotiated family supports operator-controlled list data for Atomic #55. It does not grant chain coverage, initialization, state readiness or database access. Providers return one ordered entry for every distinct requested name, including an empty array for either complete missing or empty lists; `complete: true` and native attempt totals are mandatory. Unavailable, malformed, partial, mismatched and over-budget results fail closed. The host must batch all distinct names into one invocation per request so the limits are request totals, and the provider must enforce the supplied aggregate limits while reading; reported native attempts are provider assertions, not a measured proof by the SDK. UTF-8 bytes count requested names once and all returned item occurrences. Names and items are not interpreted by the SDK. Results are detached and frozen.

The host selects the configured source and its configuration generation, supplies cancellation/deadline and lifetime guard, and must bind that identity and generation to its state request and final response/cache publication. The host must guard through serialization and publication; this helper cannot establish that authority. It may call the list helper before one existing state composition; it does not consume a state compose. Unconfigured sources fail unavailable when needed.

The original Atomic list cache uses a five-minute max age. A configuration/source generation change must not mix sources, but an ordinary data update does not automatically invalidate a still-valid cached result. Source identity, configuration generation and relevant state versions belong in cache keys; providers/hosts must explicitly preserve the five-minute behavior for parity and test updates across that interval. A cached result can contain older data. This contract neither implements a cache nor claims snapshot isolation across operator data and chain state. HAPI #414 owns source provisioning, native MongoDB adapter, lifecycle and onSend enforcement. SDK tests do not prove those integrations or API parity.
